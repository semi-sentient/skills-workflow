# Fix cycles: failures, budgets, retries, and mid-run plan drift (SKILL.md Step 4)

Read this the first time a run routes anything to a fix — a Code summary reporting a blocking failure, a reviewer's NOT MET, an out-of-criteria defect or weak-criteria flag routed to a fix, a hook failure, a sub-agent that died with no return, or a review finding that says the plan's own text is wrong. A run whose phases all pass first time never needs it. SKILL.md carries the budget numbers and the never-rules; this file carries the procedure.

## Error handling

When a Code agent's summary reports failures, or a Review agent returns NOT MET verdicts:

1. **Assess severity** — Can the next phase proceed, or is this blocking?
2. **If non-blocking** — Note it in progress, carry forward as context, continue
3. **If blocking due to a bug or test failure reported in a Code agent's own summary, or by the human at a human gate in a report that names committed code** (NOT MET verdicts route via Step 4 item 5's counted Code re-attempt instead, never here; a gate report naming no committed file is human-gate.md's Diagnose route, which draws no retry) — Spawn a Debug agent (agent-operations.md → Debug, brief composed there) with the failure description from the Code agent's summary, the files and code sections involved, and what was being attempted
4. **If blocking due to insufficient context** — The Code agent may report that it couldn't complete the work because it didn't understand an existing pattern, couldn't find the right interface, or lacked context about how something works. Spawn a Research agent scoped to the missing context, tier picked by Step 3's destination rule: findings the re-attempt brief will point at are file-destined — resolve the path first, suffixing it if the filename already exists (an earlier brief may point at the original), and the agent writes the file itself; a single missing fact is an inline lookup, inlined into the retry brief's `DELTAS`. For a file-backed spawn, apply Step 3's write-scope check in its mid-run form: snapshot `git status --porcelain` before the spawn and compare after (the tree legitimately holds phase work). Then re-attempt the phase with the additional context included
5. **After Debug or retry resolves** — Verify the fix is sufficient, then proceed to the review gate (Step 4 item 5): post-fix changes are unreviewed by definition, and the gate re-runs before checkboxes are ticked or the phase is committed — full by default, scoped only when the Scoped Re-review Exceptions apply (agent-operations.md). (For non-Code phases, or runs where the gate is skipped, continue directly.)
6. **If resolution fails** — Report to the user with full context and ask for guidance

## Budgets

**Retry limit.** A phase may be retried a maximum of 2 times (original attempt + 2 retries). The limit counts every **failure-driven** fix cycle on the phase — one triggered by a NOT MET verdict or a blocking failure — regardless of route: a Debug intervention (item 3) and an enriched-brief re-attempt (item 4) each consume a retry, exactly like a Code re-attempt from a NOT MET verdict. (A fix cycle on a phase whose criteria all stand MET draws on the corrective-pass budget below. Item 4's Research spawn is read-only context gathering and consumes nothing — the re-attempt it feeds does.) Exceptions that consume neither a phase retry nor a corrective pass (each carries its own bound, named where it is defined): a Debug agent spawned for a pre-commit hook failure (below — a NOT MET from the post-fix re-review routes to item 5's counted path, and the re-attempted phase's eventual commit starts a fresh two-attempt count), the commit fallback's single message re-author (the diff is unchanged), and the Corrective-pass budget's deletion-only pass (bounded there at one per phase; ledger Note `deletion 1/1`, tracker flag `(↻ deletion 1/1)`). After the limit is exhausted, escalate to the user regardless of failure type, including the last Code agent's summary and the last Review agent's returned verdicts and findings (if any).

**Corrective-pass budget.** A separately-counted budget of 2 fix cycles per phase for correcting findings surfaced while every criterion stands MET — an out-of-criteria defect (Step 4 item 5's routing), a test gap, a small fix the phase would otherwise commit as a known flaw. The two slots are not interchangeable. The first pass takes the routed finding set whatever its classes. The **second** slot has exactly one admission: the re-review reported a finding tagged `behaviour` (the Review return's defect-class tag). A re-review whose findings are all `documentation` ends the phase's fixing — those findings are carried (Step 4 item 10), never fixed: the run record shows a passing phase's second pass is almost always comment polish, and its full re-review costs as much as the first. One named exemption, classified before either slot rule is applied: a **deletion-only pass** — every ordered change is a comment deletion under the Retry protocol, no rewrite — draws no slot, whether or not a slot remains and whatever the findings' tags, and is bounded at one per phase beyond the budget (its ledger Note reads `deletion 1/1` and its tracker flag `(↻ deletion 1/1)`, which is how the bound survives compaction); its brief orders each touched file marked `[comment-only]` (Completion Requirement), so Exception 2's scoped re-review follows; an unmarked file forces the full re-review as always. It exists because a false comment shipping is worse than polish, and deletions have never needed a second pass; it never covers missing documentation, only a comment a finding names as false, stale, over-broad, or restating the code. When the second slot IS drawn, the brief carries the whole routed set, `documentation` findings included (One fix cycle per review). A finding returned without a tag routes as `behaviour` — the orchestrator never classifies it by reading the cited code (Context Discipline); the brief's tag requirement is what keeps this arm rare. The budget is a ceiling, never a target — a phase with nothing routed to a fix draws nothing. The counting rule is mechanical, never a judgment call: a fix cycle triggered by a NOT MET verdict or a blocking failure counts against the retry limit; every other pre-commit fix cycle counts against the corrective budget, except the exempt spawns the Retry limit names, which draw neither. Neither budget draws on or refreshes the other. A corrective pass is a post-verdict change like any other — Step 4 item 5's invariant applies unchanged: fresh re-review, full by default, scoped when its narrow exceptions hold (an additive test pass or a comment-only fix qualifies for Exception 2's scoped path). If that re-review returns any NOT MET, the phase has genuinely regressed: route through the failure path, subsequent cycles counting against the retry limit. When the corrective budget is exhausted, stop fixing (sole exception: the deletion-only pass above is exempt and may still run its one bounded pass): note the remaining findings in the progress output and carry them forward (phase report, and the PR's Review notes where applicable) — without the split, polish on a passing phase would consume the failure budget, exactly backwards. A carried finding that shows a plan-specified value or invariant is wrong is also surfaced as drift (below) — the user amends or proceeds, and either answer is written into the plan there.

## Composing a fix-cycle brief

A retry or corrective pass is a Code brief (`brief-code.md`) whose `FIX_CYCLE` slot is filled instead of `None`, written to `phase-<n>-brief-code-<k>.md` (`k` = 2, 3, … per fix cycle) — never over `phase-<n>-brief-code.md`: the Review brief's `CODE_BRIEF_PATH` names that first brief, and a fix-cycle brief's `FIX_CYCLE` block carries failed-attempt material a reviewer must never see. Findings are cited **by reference, never quoted**: the reviewer numbered them `F1, F2, …` identically in its return and in the evidence file, so the slot names the file and the numbers and the fix agent reads them there. Do not retry the same phase with identical instructions. The slot carries, in order:

1. **Budget line** — `retry 1/2`, `corrective 2/2`, or `deletion-only 1/1` (mirrors the ledger Note).
2. **Findings to fix** — `F2, F3 in <scratch_dir>/phase-<n>-review-2.md — read them there; fix every one in this pass` (One fix cycle per review: the brief carries the review's entire routed finding set — every NOT MET and every defect or flag the routing sent to a fix — never a subset while other routed findings wait; findings judged not worth fixing are noted and carried in the same turn). For a Code-summary or human-reported failure, the failure description in 2–3 sentences instead.
3. **Failed-attempt observations** (retries only) — 2–3 sentences on the approach the failed attempt took and the decisive error output from its summary, labelled as observations from a failed attempt that the retry agent should verify independently rather than trust.
4. **Comment orders** — per the Retry protocol below: `delete the comment at <file:line> named by F3; write nothing in its place` or `rewrite the comment at <file:line> (required-by: …); verify every clause against the code`.
5. **Working-tree statement** — one of the two forms below, decided before spawning; never undefined (an undefined tree lets a retry duplicate edits, and lets the commit's `rp.sh stage` commit half-applied leftovers).
6. **Message file** — `commit-message file: <path> — the fix-cycle message-maintenance rule in run-conventions.md applies; check whether the file exists`. Every touched file is marked `[comment-only]` in the summary when the change is comment-only.

**Working-tree statement.** Corrective pass: `the phase's work is staged; build on it`. Retry, default: **revert the failed attempt** — revert exactly the files in its Files-changed list, including any files a Debug agent modified while fixing this attempt (from its fix-applied report), minus any keep-dirty path, which is never reverted or deleted (a keep-dirty path on a Files-changed list holds the user's own uncommitted edits, so leave it and note it in the brief; `rp.sh delta` respects the same exclusions, and `tree-state.md` is the authority when the in-memory value is gone) — and delete any new files it created, then `rp.sh cleanup <n>` (message file and baselines go together, so a stale message can never ride a later fast path nor a stale baseline mislead a later scoped review). Never blanket `git checkout -- .` (the tree legitimately holds the plan file's checkbox edits and any keep-dirty paths). Unstage first if the failed attempt was staged in Step 4 item 5. State in the brief: `tree is at phase start`. Retry, alternative: **keep partial work** only when the failed summary shows it cleanly passing some acceptance criteria — `tree contains partial changes to <files> — build on them`.

## Retry protocol — comments

In any fix cycle — retry or corrective pass alike — the pass corrects the code *and its comments* to describe current behaviour only, never a record of the attempt it replaces (git history holds that), and the brief must not ask the agent to preserve it. When a review finding names a comment as false, stale, over-broad, or restating the code, the very next fix cycle's brief orders the comment that finding names **deleted**, nothing written in its place — on first contact, never only after a rewrite has failed: a missing comment is a smaller defect than a false one, and in production, rewrites repeatedly replaced one false claim with another across consecutive passes while deletions survived review first-time. Two named exceptions, each admitted only by the reviewer's `required-by:` token on the finding — never by the orchestrator's own reading of the comment or the code: (a) `required-by: criterion C<k>`; (b) `required-by: guidance <file:line>`. A finding with `required-by: none`, or with no token at all, is a deletion. In either exception the brief orders a rewrite of that one comment, every clause verified against the code. If the re-review finds the rewrite false: under (a) escalate to the user with both findings; under (b) the next brief orders deletion — a deletion-only pass (Corrective-pass budget); if the phase's one deletion-only pass is already spent, the false comment is carried and named in the PR's Review notes. Never a third rewrite. Nothing else is an exception — not that the comment is useful, not that a constant would go unexplained, not that a budget or invariant "must be documented somewhere": in production exactly those grounds produced three consecutive false rewrites of one comment, while nine ordered deletions all survived review first-time. The deletion pass's re-review brief names the deletion as ordered via its `SANCTIONED` slot: an absent comment the orchestrator ordered removed is not a defect.

## Pre-commit hook failure (Step 4 item 7)

Spawn a Debug agent with the hook output, files involved, and what was being committed (`no budget` in its ledger Note). After Debug fixes the issue: if a scoped exception applies, run `rp.sh baselines` BEFORE re-staging (the fix is not in the index yet); then `rp.sh stage` and re-run the review gate with a fresh Review agent per item 5's invariant (the fix changed the diff; skip only when the gate is skipped for this run). If the re-review returns any NOT MET: first re-run item 6 in full against the new verdicts — `rp.sh untick` the criteria no longer MET (be explicit: remove those ticks) and, in active mode, `rp.sh sync` with item 6's escalation on failure, so neither the local file nor GH overstates progress; then route through item 5's NOT MET path (counts against the phase retry limit) — never directly to the commit; the re-attempted phase's eventual commit starts a fresh two-attempt count. Otherwise — including when the gate is skipped for this run (no re-review, no verdicts to reconcile) — reconcile any MET ↔ NEEDS-RUNTIME drift by re-running item 6 in full, then retry the commit via the fallback path (a Debug fix invalidates the fast path). If the second attempt fails, escalate to the user with full context. **Never bypass hooks with `--no-verify`.**

If a commit-msg hook rejects the fallback's message, that is a message problem, not a code problem: re-author the message against the hook's output and retry the commit once — the diff is unchanged, so no Debug agent, no review re-run, and no charge against the phase retry limit; if the re-authored message is also rejected, escalate to the user with the hook output.

## Infrastructure death

A sub-agent that dies with no return at all (an API or host error, never a reported failure) is not a failure-driven fix cycle — it consumes no retry and no corrective pass. Clean up in two moves, touching only what the dead agent itself could have produced. **Scratch:** `rm -f` exactly the files its brief assigned THIS agent to write — its evidence, handoff, or research file, and the commit-message file when its brief was a Code brief (an interrupted update cannot be trusted; the re-spawn authors fresh via the message-maintenance rule's absent-file arm). Never any other scratch file: research files it was told to read, a prior agent's handoff, `run-conventions.md`, the brief files, spec files, and scoped-review baselines are the run's inputs, not the dead agent's leavings. **Tree:** clear writes attributable to it, identified mechanically, never by eyeball. Four cases, matched by tree state, never by the agent's label: (1) a pre-spawn snapshot exists (Step 3's mid-run form) → its delta is the dead agent's: clear it as in case 2 — restore tracked paths from the index (`git checkout -- <paths>`; never a HEAD-sourced form, which rewrites the frozen reviewed index), delete untracked ones. (2) The phase's work was already staged (a death in a post-review fix cycle) → the unstaged-plus-untracked delta (`rp.sh delta`) is the dead agent's: restore the tracked paths from the index (`git checkout -- <paths>`) and delete the untracked files — the restore trusts the index, acceptable only because the forced-full re-review below sees everything that index holds. (3) The tree held nothing of the phase when the dead agent spawned — an initial attempt, or a retry after the default revert → all observed dirt is its own: revert per the retry default-revert rules with that dirt as the file list. (4) Another agent's phase work sits unstaged (a blocking-failure Debug or a kept-partial-work retry spawned before item 5's staging) → no mechanical rule can separate the dead agent's edits from that work: revert nothing. Exemptions, in every case: never a keep-dirty path (consult `<scratch_dir>/tree-state.md`), never `<plan_file_path>`, and never a path the dead agent's brief named as kept partial work — kept work and dead edits cannot be mechanically separated, so those paths are left exactly as found. Then re-spawn once with the otherwise-identical brief — three sanctioned adjustments: the message-maintenance rule re-evaluates the file-exists test on its own (the cleanup may have flipped it); in case 4, or whenever an exempt path may carry the dead agent's edits — a kept-partial path, or a keep-dirty path its File Manifest sanctioned it to edit — add one line to `DELTAS` saying so, for the re-spawn to verify rather than trust; and re-spawn a dead scoped reviewer as a full Review agent, per the next sentence — and append a ledger row for the death (`n/a` figures, Note names the death; the re-spawn carries the Note its dead predecessor would have — the cycle is charged once). Because a dead agent may have touched the index unseen, the re-review that follows any no-return death between a verdict and the phase's commit is always full, never scoped — the dead reviewer's own re-spawn included — `git diff --cached` shows the true staged state, while `git show :<path>` baselines would trust an index the death made unprovable. A second no-return death of the same spawn escalates to the user. (Step 4 item 5's verdict-without-file re-spawn is this same principle applied to a partial return.)

## Plan drift found mid-run

Drift discovered after Step 3's batch — a Code agent's deviation report, a review finding that shows a plan-specified value or invariant is wrong (the finding quotes the plan) — is surfaced when found by the same procedure as the batch: one message, plan text quoted, HEAD fact, the same two dispositions (**amend** or **proceed as written**), a sanctioned stop (Step 4 item 11). A retry follows a plan-contradiction NOT MET only on "proceed as written". On "amend", edit the plan file — anchor the edit on the plan's own text: the `C<k>` labels exist only in the index and spec files, never in the plan — run `rp.sh extract` (the spec files must match the plan the agents are held to), and in GH mode `rp.sh sync` (on failure, Step 4 item 6's `retry` / `continue` / `abort` escalation) before continuing; "proceed as written" appends ` (accepted as written — <one-line HEAD fact>)` to the affected criterion or sentence, so the decision survives compaction and reaches the phase report and the PR's Review notes.

An amendment that rewords a criterion of the **current** phase voids that criterion's standing verdict: untick it, and the phase's next Review spawn is **full**, never scoped (a reworded criterion needs the full-context reviewer). If no Review spawn would otherwise follow before the phase's commit — including when the diff has not changed since the last verdict — spawn a fresh full Review agent anyway: a verdict rendered against superseded wording never ticks a criterion, and the orchestrator re-running the criterion's command itself is not a review. An amendment to a **future** phase's criteria has no verdict to void and simply stands. An amendment touching an **already-committed** phase does not reopen it and its ticks stand (they were verified against the wording current at commit time): append ` (amended after commit — <reason>)` to the reworded text so the change is durable, and list it in Step 5's caveats. Exempt from all three arms: the gate amendment of a human-form criterion (human-gate.md → Diagnose route, item 6) — it holds no verdict to void, spawns no reviewer, and carries its own ` (gate: …)` suffix instead of this paragraph's.
