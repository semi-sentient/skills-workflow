# Human-gate criteria (SKILL.md Step 4)

Read this when `plan-index.md` shows a `Human-form criteria:` or `Human-gate literal:` line for any phase, or when a reviewer returns `HUMAN-GATE`. A plan with neither never needs it.

## Identification is mechanical, once, at Step 2

The human-form criteria of a phase are every acceptance criterion whose text begins with the word `Human` followed by a space (`Human verifies …`, `Human applied …`, `Human confirms …` — case-insensitive, after the checkbox and any leading emphasis or backtick). `rp.sh extract` applies this rule and lists the labels on the phase's `Human-form criteria:` line in `plan-index.md`.

A phase whose text — heading, prose, or criteria — contains the literal `Known risk`, `human gate`, or `not agent-completable` (all case-insensitive), and not the literal `(human-form set confirmed)`, has an **unresolved set** however many `Human …` criteria it already carries (in production, one labelled criterion sat beside three unlabelled human-only ones). The index marks it `Human-gate literal: UNRESOLVED`. Name it at Step 2 (item 4) and ask in Step 3's batched drift message which of its non-`Human` criteria are human-form — the classification is the user's, never inferred from intent — then make the answer durable in the plan file with the other amendments: amend the named criteria to the `Human verifies …` form, and in every case append ` (human-form set confirmed)` to the line that carries the literal; then `rp.sh extract`. Either way the mechanical rule alone settles the phase for the rest of the run and any resume; a classification held only in conversation is lost at compaction.

## The gate is on criteria, never on the phase

A phase still runs the normal loop for every criterion an agent can own — Code agent, review gate, commit — with BOTH the Code brief and the Review brief naming the human-form criteria as outside their mandate (their `HUMAN_FORM` slot lists the labels; the reviewer returns `HUMAN-GATE` for each in place of a verdict; Step 4 item 5 routes that as no action; the Code agent never satisfies one by proxy or contorts it into a mechanical pass). A phase whose criteria are all human-form spawns no Code agent and no reviewer.

Then, once the agent-owned work is committed (or there is none): end the turn with a checklist — every human-form criterion verbatim (from `rp.sh criteria <n>`) and what the human must observe for each — as a sanctioned stop (Step 4 item 11). The checklist ends with one standing line: *if a criterion fails, say what you observed and which read-only commands a diagnosis may run.* Where a criterion's text is itself a read-only command with a checkable output, the checklist offers to run it, and whichever shell produced the output the human ticks on is recorded in the progress note (an operator's shell and the orchestrator's can resolve different binaries). At the gate the orchestrator runs commands only at the human's explicit direction — read-only checks the human delegates back (`terraform plan`, an `aws … get-*` read) are the normal shape — report the check's result back to the human and tick only on their confirmation: delegation makes the orchestrator the human's eyes, never the author of their report; a mutating operation the human directs is theirs to authorize and is recorded in the progress note. Human-form criteria are ticked only from the human's report — never from the orchestrator's own evidence, never from a reviewer's verdict; a reviewer marking one NEEDS-RUNTIME does not make it item 6's checked-but-tagged case.

## The human's reply

The reply takes one of three shapes, and **results** may arrive incrementally across several exchanges (tick each criterion per item 6 as the human confirms it; the gate stays open); a reply that is none of the three is re-asked once, then treated as `defer`:

- **results** — tick what the human reports passed per item 6 and commit that plan-file edit as a checkbox-only commit via item 7 (`(no commit — no changes)` where the plans directory is git-ignored). A reported failure — or a delegated read-only check that fails — takes exactly one of the two routes below, decided by where the report locates the failure; then re-present the checklist for every criterion still unticked. The gate repeats until the human reports all passed, says `defer`, or the route's bound is reached (escalate as each route says).
- **`defer`** — leave the criteria unticked, flag the phase `(⚠ human gate — deferred)` in the tracker, and carry every deferred criterion to Step 5's caveats and the PR Test plan (completion-templates.md's population rule, source c) — `<outcome>` is then `partial` by definition and Step 5's partial templates apply, but a resume re-presents the checklist for the deferred criteria rather than re-attempting the phase (branch-and-resume.md → Resumability).
- **`stop`** — end the run at this phase as `aborted` (a user abort, per `<outcome>`'s definition).

The gate stops the run at the phase's position in the plan, wherever that is; never reorder it to the end or fold it into Step 5.

## A failure at the gate: two routes, no overlap

The routing test is mechanical: **does the report name committed code?** A report that names a repository path, a test, or the behaviour of the phase's own diff (`the new handler returns 500`, `src/x.ts throws`) has located the failure in the repo. Every other report has not — an environment, a tool version, a credential, a live resource's state, a network path, a timing window, a shell that resolves a different binary. Nothing in the repo is wrong until evidence says so, and the orchestrator does not go looking for that evidence itself.

**Debug route — the report names committed code.** A blocking failure in the phase's committed code: spawn a Debug agent with the human's observation (fix-cycles.md item 3), run the review gate, commit, counting against the phase's retry limit; exhausted → escalate per fix-cycles.md.

**Diagnose route — the report names no committed file.** One read-only spawn, then the human's choice. Beyond `rp.sh` housekeeping and the item-7 commit, the orchestrator's shell runs exactly two kinds of command on this route: the recovery the human directs, and the criterion's re-verification. No diagnostic command at any point — no `ps`, `lsof`, or `describe`, no log or source read, before, during, or after the spawn, even at the human's direction: a diagnostic the human wants run is a `Needs:` authorisation for item 5's follow-up spawn, and a question the digest left open goes back to the human as that authorisation or a choice, never to the orchestrator's own shell.

1. **Authorised commands.** The closed read-only list comes from the human's report (the checklist asked for it). A report that names none is answered with one question — which read-only commands the diagnosis may run — before anything is spawned; the orchestrator never composes the list itself, and never runs a diagnostic command of its own at this point: not a console pull, not a `describe`, not a log read. The criterion's own check, when the human already delegated it, is a verification the orchestrator ran at their direction; *why* it failed is the agent's question.
2. **Spawn.** `rp.sh brief brief-diagnose.md phase-<n>-brief-diagnose-C<k>.md …` (Brief recipes) with the human's report verbatim in `HUMAN_REPORT`, the list in `AUTHORISED_COMMANDS`, and `DIGEST_PATH=<scratch_dir>/phase-<n>-diagnose-C<k>.md`; spawn one **Diagnose** agent (`general-purpose`; the template is its whole definition) with the standard pointer line. Ledger row: `rp.sh ledger <n> Research <tokens> <tool_uses> <duration_ms> "" "diagnose C<k>"` — it draws no retry and no corrective pass; its bound is the next paragraph.
3. **Relay.** Return the digest to the human unchanged and ask which option they take; the message's own recommendation (Step 4 item 11) is the digest's `Recommend:` line, and the orchestrator adds nothing the digest did not say. A `Needs:` line naming commands the list lacked goes in the same message. A digest whose `Cause:` locates the failure in committed code hands off to the **Debug route** above with the digest as the failure description — the routes meet only here, and the Debug spawn then counts as that route says.
4. **Recovery.** The human performs the chosen option, or directs the orchestrator to (a mutating command runs only at that direction, named, and is recorded in the progress note). A directed recovery the orchestrator's shell cannot reach — the process, service, or resource lives on the human's machine or behind their credentials — is reported in one line (the command and what it returned) and the choice is put back: another option, `defer`, or `stop`; no investigation follows — not by the orchestrator, and not by a spawn beyond item 5's named exception, which an unreachable recovery does not open. Then the criterion is re-verified exactly as the checklist verifies anything — the human's report, or a delegated read-only check — and ticked per item 6 on their confirmation.
5. **Bound: one Diagnose spawn per failure.** One named exception, both conditions required: the digest's `Cause:` was `unconfirmed` AND the human authorises the commands its `Needs:` line named — then one follow-up spawn, same brief with the list extended, and no third under any condition. A second failure of the **same criterion** after the chosen recovery is not diagnosed again: escalate to the human with the digest path and exactly two options, `defer` or `stop` (a run whose environment defeats one diagnosed recovery needs the human's judgement, not a second guess). A different criterion failing is a new failure with its own single spawn.
6. **Record.** Every Diagnose-routed failure leaves a durable mark in the plan, written before the gate is re-presented: append ` (gate: <cause in ≤10 words>; recovery: <chosen option in ≤10 words>; digest <path>)` to the criterion's text, and where the recovery changes what the human verifies — a different method, a different resource, a different command — reword the criterion to what was actually verified. Mechanics are fix-cycles.md's mid-run drift: edit the plan file anchored on its own text, `rp.sh extract`, and in GH mode `rp.sh sync`. A human-form criterion holds no verdict (the reviewer returned `HUMAN-GATE`), so this amendment voids nothing and spawns no reviewer. The digest file is offered as the body when the human asks for an issue to be filed or extended; the orchestrator files none unasked.

## Waiting on an operation

A gate often waits on an operation with a terminal state — a replacement task, an instance refresh, a snapshot, a deploy. The wait is **one call**:

```bash
rp.sh wait "<command whose output is the state>" "<terminal states as an anchored regex>" <timeout_s> [interval_s]
```

It polls the command until its output matches the regex or the timeout passes, and prints the final state only — one line, never the intermediate ones. Name every terminal state in the regex (`succeeded|failed`, `InService|Cancelled`) so a failure ends the wait instead of running it to the timeout. Never a Monitor stream, never a background task whose output file is read again and again, never a sleep-and-check spread across turns: in production the poll stream became the orchestrator's largest single context source (§5 of the third live-run report on #6 — 16 of 17 `Read` calls; 23 Monitor ticks in the run before it). A wait longer than the host's per-call limit is still one call: run the same `rp.sh wait` as one background task and read its output once, when the host reports it finished. **Named exception — no queryable terminal state** (completion shows only in a log stream or to a human): one bounded background task (`timeout`-wrapped, or the stream's own `--since`/`--until` bounds) and one read of its output at the end.

**Evidence commands** at the gate — a delegated check, the state read the human asked for — default to `--query`/`--output text` (or the tool's equivalent projection) written to `<scratch_dir>/evidence-<what>.txt` and `tail -n 3`'d into the turn; `--output json` is used only when the JSON itself is the criterion's evidence. The file is what the human, the handoff, and any issue cite; the three lines are what the orchestrator carries.

## An unplaced `HUMAN-GATE` return

A `HUMAN-GATE` on a criterion the brief did NOT place is a question for the user (a sanctioned stop, Step 4 item 11): "human-form" amends the criterion to the `Human …` form (re-extract, sync per item 6); "agent-verifiable" re-spawns the reviewer once, no budget, with the criterion named as agent-verifiable in its brief's `HUMAN_FORM` slot — a second `HUMAN-GATE` on it escalates to the user with both returns. Resolve an unplaced `HUMAN-GATE` before any other routing of that review.
